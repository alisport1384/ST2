## ۲) جزئیات هر تغییر

### ۲-۱) §۴-۸ — حد ضرر از تایید میانی

**متن سند (خطوط ۳۶۰–۳۶۳):**
> **حد ضرر:**
> - **خرید:** کف تایید میانی **منهای ۲ تیک** بافر.
> - **فروش:** سقف تایید میانی **به‌علاوه‌ی ۲ تیک** بافر.
> - تعداد تیک بافر قابل تغییر است.

**کد قبل:**
```kotlin
s.sl = if (bull) s.hvL - cfg.slBufTicks * cfg.mintick else s.hvH + cfg.slBufTicks * cfg.mintick
```

**کد بعد (`Engine.armSetup`):**
```kotlin
val slBuf = cfg.slBufTicks * cfg.mintick
s.sl = when {
    !s.midRef.isNaN() -> if (bull) s.midRef - slBuf else s.midRef + slBuf
    else              -> if (bull) s.hvL - slBuf   else s.hvH + slBuf   // فقط اگر midRef موجود نبود
}
```

- «تایید میانی» در کد همان `s.midRef` است؛ برای خرید = کف تایید میانی، برای فروش = سقف تایید میانی. ✅ مطابق سند.
- بافر ۲ تیک از تنظیمات خوانده می‌شود (`slBufTicks`، پیش‌فرض ۲) و برچسبش در اپ به «بافر حدضرر (تیک) — از کف/سقف تایید میانی» تغییر کرد.
- سطح سفارش **بدون تغییر** ماند و همچنان از باکس HV ساخته می‌شود (§۴-۸ خطوط ۳۴۶–۳۴۹).

**اثر جانبی مهم که باید بدانید:** چون فاصلهٔ حد ضرر حالا از کف/سقف تایید میانی حساب می‌شود و نه از کف باکس HV، این فاصله در بیشتر موارد **بزرگ‌تر** می‌شود. این فاصلهٔ بزرگ‌تر مستقیماً با دروازهٔ §۱۸-۳۱ (`SL > N` ⇒ سفارش ثبت نشود) برخورد می‌کند؛ با پیش‌فرض جدید `N = 20` تعداد سفارش‌های ردشده به‌خاطر `SL>N` نسبت به قبل کمتر می‌شود، اما این دو قاعده به هم وابسته‌اند و باید در بک‌تست با هم دیده شوند.

### ۲-۲) §۴-۹ — بازگشت به قاعدهٔ «فقط کلوز»

**متن سند (خطوط ۴۴۵–۴۴۹):**
> خرید: اگر بعد از پر شدن و باز شدن سفارش یک کندل تریگر۲ خارج از سطح oo خرید بسته شد و کاملا بالا تر از سطح oo بسته شده بود، حد ضرر به سطح oo خرید منتقل میشود.
> فروش: ... کاملا پایین تر از سطح oo بسته شده بود ...

**کد قبل:** سه شرط هم‌زمان (کلوز بیرون از باکس HV + کل کندل آن‌سوی oo + عدم لمس oo).
**کد بعد (`PaperBroker.manageBar`):**
```kotlin
if (!sameEntryBar && !t.be && t.slAdj.isNaN()) {
    val oo = t.entry
    val moved = if (bull) cd.c > oo else cd.c < oo
    if (moved) { t.slAdj = oo; /* لاگ + آلارم */ }
}
```
شرط‌های «باکس HV» و «کل کندل آن‌سوی oo» برداشته شد؛ متن لاگ هم به همان عبارت سند برگشت. ✅

نکته‌های حفظ‌شده (خارج از این بند سند ولی لازم): کندلِ ورود (`sameEntryBar`) مشمول نیست، انتقال فقط یک‌بار انجام می‌شود (`t.slAdj.isNaN()`)، و اگر سر‌به‌سر قبلاً فعال شده باشد (`t.be`) دوباره اجرا نمی‌شود.

### ۲-۳) §۲۰-۲ (Mixed) — صفر شدن `lost`

**متن سند (خط ۷۳۸):**
> در مود Mixed در صورتی که capital مجدد به کمتر از M رسید (Capital<M) بخش ManageNothing مجدد فعال میشود ... و مقدار lost = 0.0 میشود.

**کد (`MoneyManager.onCapitalUpdated`):**
```kotlin
fun onCapitalUpdated(capital: Double) {
    if (cfg.mmMode != MoneyMode.MIXED) return
    while (nakedCapital() > 0.0 && capital / nakedCapital() >= 2.0 && guard++ < 64) naked = nakedCapital() * 2.0
    if (capital <= growthLimit()) lost = 0.0     // ← افزودهٔ این نسخه
}
```
دقیقاً مطابق `if Capital>M → ManageCM  else if Capital<=M → ManageNothing` در سند. ✅

### ۲-۴) §۱۸-۳۱ — پیش‌فرض N = ۲۰

**متن سند (خط ۸۱۹):** «مقدار N در تنظیمات قابل تغییر است و به طور پیش فرض عدد 20 است.»

- `Settings.maxSlUnits`: از `3.0` به `20.0` تغییر کرد.
- `Store.SPEC_REV`: از `4` به `5`.
- مهاجرت: هنگام بارگذاری تنظیماتِ ذخیره‌شدهٔ قدیمی، **فقط اگر مقدار دقیقاً ۳٫۰ بود** (یعنی همان پیش‌فرض نسخهٔ قبل که کاربر دستش نزده) به ۲۰٫۰ تبدیل می‌شود؛ هر عدد سفارشی دیگری دست‌نخورده می‌ماند. این کار عمدی است تا انتخاب دستی کاربر پاک نشود.

## ۴) جاهایی که کد هنوز ۱۰۰٪ با سند یکی نیست (پوشانده نشده — فهرست کامل)

۱. **§۱۸-۳۱ — مثال درون سند با پیش‌فرض جدید نمی‌خواند.**
   سند در خط ۸۱۶ مثالش را با `N = 3` نوشته و می‌گوید سفارشی با `sl = 5` **ثبت نمی‌شود**. ولی دو خط بعد (۸۱۹) می‌گوید پیش‌فرض N = ۲۰ است. با N = ۲۰ همان سفارش **ثبت می‌شود**. کد پیش‌فرض ۲۰ را گرفته (طبق جملهٔ صریح)، پس مثال خط ۸۱۶–۸۱۸ عملاً دیگر نمونهٔ «رد شدن» نیست. **این تناقض داخل خود سند است و من حق تغییر سند را ندارم**؛ اگر منظورتان این بوده که مثال باید ملاک باشد (یعنی عدد کوچک‌تر)، بفرمایید تا پیش‌فرض را برگردانم.

۲. **§۱۰ «فیلتر ساعت معاملاتی ندارد» در مقابل §۲۵–۳۰.**
   خط ۵۰۹ صریحاً می‌گوید فیلتر ساعت معاملاتی (فعلاً) وجود ندارد، اما بندهای ۲۵ تا ۳۰ پنجرهٔ ۰۱:۳۰–۲۰:۰۰ UTC، بسته‌شدن سفارش‌ها راس ۲۰:۰۰ و ممنوعیت سفارش‌گیری در بازار بسته را الزام می‌کنند. کد **بندهای ۲۵–۳۰ را پیاده کرده** و فیلتر ساعت را دارد (`MarketHours.isOrderWindow` در `Engine`، `PaperBroker`، `OrderWindowTest` با ۷ آزمون). اگر منظورتان حذف کامل پنجره است، این تغییر بزرگی است و منتظر تأیید شما هستم.

۳. **§۱۸-۲۱ در سند وجود ندارد، ولی قاعده‌اش در کد فعال است.**
   کد پس از لمس ناحیهٔ ساختار، با گذشت **یک کندل ساختارِ کامل** ناحیه را «مصرف‌شده» علامت می‌زند و در حالت‌هایی ستاپ را می‌بندد (`Engine.kt` حدود خطوط ۴۶۰–۵۰۰). این قاعده در ویرایش فعلی سند نیست (بند ۱۸-۲۱ حذف شده) و از نظر لغوی با §۴-۵ («تعداد ناحیه‌ها نامحدود است؛ ناحیه‌هایی که باطل نشده‌اند باید ثبت شوند») هم‌پوشانی دارد. **این تنها جایی است که کد یک قاعدهٔ اضافه دارد که سند آن را نمی‌خواهد.** عمداً دست نزدم چون حذفش رفتار مسیر ستاپ‌ها را جدی تغییر می‌دهد و می‌خواستم اول نظر شما را بدانم.

۴. **حد ضرر: بازگشت اضطراری به باکس HV.**
   اگر به هر دلیلی `midRef` مقدار معتبر نداشته باشد (NaN)، کد به کف/سقف باکس HV برمی‌گردد تا سفارش بی‌حدضرر نماند. سند چنین حالتی را تعریف نکرده. این مسیر در عمل نباید فعال شود (چون سفارش فقط بعد از تایید میانی مسلح می‌شود) ولی یک رفتار «خارج از سند» است.

۵. **`lost = 0` بعد از حد سود نهایی.**
   سند این قاعده را **در متن توضیح نداده**؛ فقط در مثال §۲۰ مقدار `lost = 0.0` بعد از پایان معامله دیده می‌شود (خط ۶۷۶) و در مثال `cmsnLost = 0` (خط ۷۳۶). کد آن را به‌صورت یک قاعدهٔ کلی (و یک سوییچ در تنظیمات با پیش‌فرض روشن) پیاده کرده است، از جمله صفر شدن `cmsnLost` در هر TP نهایی. اگر این تعمیم را نمی‌خواهید، سوییچ در اپ هست («با رسیدن به حد سود نهایی، Lost صفر شود»).

۶. **بک‌تست واقعی برای این نسخه اجرا نشد.**
   دیتاست بزرگ XAUUSD داخل سندباکس پایدار نمانده است (بازنشانی محیط). آزمون `RealSampleBacktestTest` روی نمونهٔ کوچک اجرا و پاس شد، ولی عدد عملکردی روی دیتاست کامل برای ۱.۴.۳۱ تولید نشده. این را پنهان نمی‌کنم: عدد بک‌تستِ تازه با حد ضرر مبتنی بر تایید میانی **هنوز در دست نیست**.
